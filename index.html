    1.10

    Common misconceptions

    Each of these costs marks in exams. Say out loud why it's wrong before you open it.

    MythBig data just means a lot of data.

    Actually: Volume is only one V. The slides define big data as data that is expensive to manage and hard to extract value from, and Variety, Velocity and Veracity can make data "big" even when it isn't huge.

    MythEach new V model replaced the one before it.

    Actually: 3Vs, 4Vs, 5Vs and 6Vs come from different people (Laney, IBM, Demchenko, Microsoft). They are different framings, not version upgrades. Know who added which V.

    MythHadoop and big data mean the same thing.

    Actually: Hadoop is one framework. In the analytics stack it sits in layer 2 (stored data processing), alongside stream platforms like Storm and Kafka, with analytics platforms, tools and solutions above it.

    MythNoSQL means you can't use SQL.

    Actually: NoSQL means data is stored and retrieved using models other than relational tables. It says nothing about the query language. Chapter 3's Hive even puts a SQL-like language on top of Hadoop.

    MythMost new data is neatly structured.

    Actually: The Oracle slide shows the opposite: about 88% of data growth is unstructured, stored by applications and sent to backup and archive.

    2.5

    MapReduce: Mapper and Reducer

    MapReduce is a method for distributing a task across multiple nodes. Each node processes the data stored on that node, where possible. It has two phases: Map and Reduce.
    Features
    • Automatic parallelization and distribution
    • Fault tolerance
    • Status and monitoring tools
    • A clean abstraction for programmers (usually Java)
    • Hides the "housekeeping"; developers just write Map and Reduce functions
    The Mapper
    • Hadoop runs Mappers on nodes holding their data locally, to avoid network traffic
    • Multiple Mappers run in parallel, each on a portion of the input
    • Reads key/value pairs; outputs zero or more key/value pairs
    • May use or ignore the input key. Reading line by line: key = byte offset where the line starts, value = line contents, key usually irrelevant
    • Any output must be key/value pairs
    The Reducer
    • After Map, all values for one intermediate key are combined into a list
    • One or many Reducers; all values for a key go to the same Reducer
    • Keys arrive in sorted order: this is the "shuffle and sort"
    • Outputs zero or more final pairs, written to HDFS; usually one pair per key
    Signatures 
    map(in_key, in_value)
  -> (inter_key, inter_value) list

map(key1, value) -> list<key2, value2>
reduce(key2, list<value2>) -> list<value3>
    # Word count mapper
Map(input_key, input_value)
  foreach word w in input_value:
    emit(w, 1)

# Input to the mapper
(3414, 'the cat sat on the mat')
(3437, 'the aardvark sat on the sofa')
# 3437 - 3414 = 23 = 22 chars + 1 newline
    # Sum reducer
reduce(output_key, intermediate_vals)
  set count = 0
  foreach v in intermediate_vals:
    count += v
  emit(output_key, count)

# Reducer output
('aardvark',1) ('cat',1) ('mat',1) ('on',2)
('sat',2) ('sofa',1) ('the',4)
    Formal view (slides 31–32)

    A job splits a large dataset into independent chunks as key-value pairs, which improves speed and reliability. The InputFormat divides input into ranges and one map task is created per range. The JobTracker distributes tasks to worker nodes. Each map's output is partitioned per reducer. Each reducer pulls its partition from the machines where the maps ran, combines it, and writes back to HDFS (Mapper ×3 → shuffling → sorting → reducer → Part 0 → HDFS replication).

    The diagram's input uses capital "The" yet the result counts the = 4, which needs a lowercase step the pseudocode never shows.

    2.7

    MapReduce in Hadoop (MRv1) and why YARN replaced it

    JobTracker (master)
    • Resource management: managing worker nodes (TaskTrackers)
    • Tracking resource consumption and availability
    • Job life-cycle management: scheduling tasks, tracking progress, fault tolerance
    TaskTracker (per-node slave)
    • Launch and tear down tasks on JobTracker's orders
    • Provide task-status information to the JobTracker periodically

    Diagram: clients submit jobs (dashed) to the JobTracker; TaskTrackers running tasks send MapReduce status (solid).

    Background: cluster computing

    A computer cluster is a set of loosely or tightly connected computers that work together so they can be viewed as a single system. Challenges: storing data persistently and keeping it available if nodes fail; dealing with node failures during long-running computations; the network bottleneck that delays processing. MapReduce answers by bringing computation close to the data. Its stated limitation: map and reduce jobs are "not stateless", so Reduce must wait for Map to finish, which limits parallelism. So YARN was born as a generic resource management and distributed application framework.

    See it: one JobTracker vs YARN

    Submit jobs to both clusters. In MRv1 every job's scheduling and monitoring lands on the single JobTracker. In YARN the ResourceManager only hands out containers, and each job gets its own ApplicationMaster.

    The slide calls JobTracker/TaskTracker the "current" system, but since Hadoop 2 they are replaced by YARN. "Not stateless" is confusing wording: the real problems were the strict map-then-reduce barrier, the single overloaded JobTracker, and MRv1 running only MapReduce jobs.

    2.8

    YARN: Yet Another Resource Negotiator

    YARN is part of core Hadoop: a next-generation framework that extends MapReduce by supporting non-MapReduce workloads. It lets multiple engines (interactive SQL, real-time streaming, data science, batch) handle data stored in a single platform, and is the prerequisite for Enterprise Hadoop, providing resource management and a pluggable architecture with predictable performance and service levels.

    Idea: split the JobTracker's two jobs (resource management and job scheduling/monitoring) into separate daemons: a global ResourceManager and a per-application ApplicationMaster. An application is a single job or a DAG of jobs. ResourceManager + NodeManager form the data-computation framework.

    2.9

    HDFS lab: store, read, fail, re-replicate

    HDFS is a Java-based, scalable, fault-tolerant distributed file system on low-cost commodity hardware, coordinated by YARN. It scales linearly and stays economical at any size. A cluster has one NameNode (metadata only) and many DataNodes (actual blocks on their local file system). Files split into large blocks (typically 128 MB), each replicated independently, 3 times in this example.

    This is the slide's exact layout: /user/diana/foo → 1, 2, 4 (amber) and /user/diana/bar → 3, 5 (teal). Tap a DataNode to kill it.

    Drag to rotate · tap a DataNode to fail it
    NameNode block map (live)
    BlockFileDataNodesReplicas
      NameNode
      • Represents files and directories as inodes: permissions, modification and access times, namespace and disk-space quotas
      • Holds the namespace tree and block → DataNode mapping, with the entire namespace image in RAM
      • Metadata: file name, permissions, block IDs, block locations, number of replicas
      • Actively monitors replica counts; recreates lost replicas
      • Never sends requests directly. It replies to DataNode heartbeats with commands to: replicate blocks to other nodes; remove local block replicas; re-register and send an immediate block report; or shut down the node
      Reading a file
      • The client asks the NameNode which blocks make up the file and which DataNodes hold them
      • It then reads directly from the DataNodes. Data never passes through the NameNode
      Master / slave layout

      Master node: NameNode + ResourceManager. Each slave node: DataNode + NodeManager + Map/Reduce tasks. Blocks are replicated across Rack 1 and Rack 2.

      Very high-level overview

      Loaded data is split into blocks (typically 64 MB or 128 MB). A Map task usually works on one block. A master program assigns Map tasks to nodes that store that block locally, so many nodes work in parallel.

      Core Hadoop concepts
      • Applications are written in high-level code; developers don't worry about network programming or temporal dependencies
      • Nodes talk to each other as little as possible; a "shared nothing" architecture
      • Data is spread among machines in advance; computation happens where the data is stored; data is replicated for availability and reliability

      Know the four heartbeat-reply commands (replicate, remove replicas, re-register and send block report, shut down), that the NameNode stores metadata only, and that clients read data directly from DataNodes.

      The diagram shows a Secondary NameNode (fsimage + edits) that is never explained. It periodically merges the edit log into the fsimage (checkpointing). It is not a live backup NameNode. Also: 64 MB was the Hadoop 1 default, 128 MB from Hadoop 2. Two slides are numbered "29" out of order.

      Points to note
      • SlidesA file is cut into large blocks (typically 128 MB; 64 MB in Hadoop 1), and each block is replicated independently on several DataNodes.
      • SlidesThe NameNode stores only metadata (namespace tree, inodes, and the block → DataNode map) and keeps it all in RAM. File data never passes through it.
      • SlidesBlocks sit on each DataNode's own local file system.
      • Beyond slidesThe last block holds only what's left. A 300 MB file with 128 MB blocks is 128 + 128 + 44 MB, and that last block uses 44 MB of disk, not 128.
      • Beyond slidesReplication multiplies raw storage: 300 MB with 3 replicas uses 900 MB of disk across the cluster.

      Data access, governance, security and operations tools

      Data access lets you interact with data in a wide variety of ways, from batch to real-time.

      Data access · SQL

      Apache Hive

      Data warehouse built on MapReduce for easy summarization and ad-hoc queries via a SQL-like interface over HDFS. User submits SQL → Hive converts it into MapReduce jobs → masters → slaves. Keeps a metadata store.

      2.13

      Common misconceptions

      Each of these costs marks in exams. Say out loud why it's wrong before you open it.

      MythThe Secondary NameNode is a backup NameNode.

      Actually: It periodically merges the edit log into the fsimage (checkpointing). It cannot take over if the NameNode fails. The slides show it but never explain it, so this is a favourite trap.

      MythWhen you read a file, the data passes through the NameNode.

      Actually: The NameNode only answers which blocks and DataNodes hold the file. The client then reads the blocks directly from the DataNodes.

      MythThe NameNode sends commands straight to DataNodes.

      Actually: It never sends requests directly. It gives instructions only as replies to DataNode heartbeats: replicate, remove replicas, re-register, or shut down.

      MythYARN replaced MapReduce.

      Actually: YARN replaced MRv1's JobTracker and TaskTracker resource management. MapReduce still runs, now as one application on YARN alongside Spark, Tez, Storm and others.

      MythReplication factor 3 means a file is cut into 3 blocks.

      Actually: The replication factor is how many copies of each block exist. The number of blocks depends on file size divided by block size (typically 128 MB).

      MythReduce can start working before the maps finish.

      Actually: Reducers need every value for their keys, so reducing waits for mapping to finish. The slides call this MapReduce's biggest limitation and the reason YARN was created.

      3.1

      Why Hive, and what it is

      Need for high-level languages
      • Hadoop is great for large-data processing
      • But writing Java programs for everything is difficult
      • Not everyone wants to (or can) write Java code
      • Solution: develop higher-level data processing languages. Hive: HQL is like SQL
      Hive is a data warehouse infrastructure tool to process structured data in Hadoop. It resides on top of Hadoop to summarize big data, and makes querying and analyzing easy.

      3.6
      Physical layout and partitions
      
      
      
        
      Physical layout (slide 18)
      • Warehouse directory in HDFS, e.g. /user/hive/warehouse
      • Tables stored in subdirectories of the warehouse; partitions form subdirectories of tables
      • Actual data stored in flat files: control-character-delimited text, or SequenceFiles
      • With a custom SerDe, any format can be used
      
        
      Partitions (slide 25)
      Partition means dividing a table into coarse-grained parts based on the value of a partition column, such as a date. This makes queries on slices of the data faster.
      • Partition keys determine how the data is stored
      • Each unique value of the partition keys defines a partition of the table
      • Partitions are named after dates for convenience
      
      
      
      
      Hive partitioning splits a table into multiple files based on partition keys. The files are organised into folders, and inside each folder the partition key's value comes from the folder's name.
      
      
      
        
      
          
      
          
        
        
        
        
        
      
        
      
        Partition pruning lab. Slide 26's query SELECT * FROM sales WHERE region = 'US' only opens the matching folders. The slide shows sales_date=2025-08; two more months are added so you can filter on both keys.

        3.7
        Buckets, and partitioning vs bucketing
        
      
        Bucketing divides table data into a fixed number of files, called buckets, based on the hash value of a specified column. Unlike partitioning, which creates separate directories by column value, bucketing spreads records across a predefined number of buckets. It can speed up certain joins, aggregations and sampling.
        
      
        
        
        Why buckets (slide 29)
        • Buckets give extra structure to the data that can be used for more efficient queries
        • A join of two tables bucketed on the same columns, including the join column, can be implemented as a Map Side Join
        • Bucketing by user ID lets us quickly evaluate a user-based query on a randomized sample of all users
        • Diagram: data → bucket ×3, based on the value of a hash function of some columns of the table
        
        
        Partitioning and bucketing (slide 30)
        Student Details → partitions Dept - ECE and Dept - CSE → each partition split into Bucket 1 and Bucket 2. The lab below builds exactly this, with your choice of bucket count.

        FeaturePartitioningBucketing
        
        
          
        OrganizationDivides data by column valuesDistributes data into a fixed number of buckets using a hash

The slide orders CSE's buckets as "Bucket 2, Bucket 1"; the order has no meaning.
        
    
        

    
        
      
        3.8
        HiveQL abilities and differences with RDBMS
        
      
        Hive Query Language provides the basic SQL-like operations (slide 19). Tap an ability for an example statement.
        
      
        
        
        
        
        
      
        
      
        Schema on read vs schema on write (slide 20)
        
        • Hive does not verify the data when it is loaded, but rather when a query is issued
        • Schema on read makes for a very fast initial load, since the data does not have to be read, parsed and serialized to disk in the database's internal format. The load operation is just a file copy or move
        • No updates, transactions and indexes

          3.11
          Common misconceptions
          
      
          Each of these costs marks in exams. Say out loud why it's wrong before you open it.
          
      
          MythHive is a database that stores my tables.
          Actually: Hive is a data warehouse layer on top of Hadoop. Table data stays as flat files in HDFS; Hive's Metastore only keeps the schema, the HDFS location and the SerDe.
          MythHive checks my data when I load it.
          Actually: Hive uses schema on read. Loading just copies or moves the file; values are checked when you query, and a value that doesn't fit its column comes back as NULL.
          MythPartitioning and bucketing are the same idea.
          Actually: Partitions are folders chosen by a column's value. Buckets are a fixed number of files chosen by a hash of a column. You can use both: buckets inside each partition.
          MythMore partitions always make queries faster.
          Actually: Pruning only helps when the WHERE clause filters on a partition column. Too many small partitions is the main risk listed on the slides.
          MythHive is good for real-time apps.
          Actually: Hive is not designed for online transaction processing, doesn't offer real-time queries or row-level updates, and its queries typically take minutes.
          MythThe Metastore holds the table's rows.
          Actually: The Metastore holds metadata only: schema, location in HDFS and SerDe. The rows are in the HDFS files under the warehouse directory.
